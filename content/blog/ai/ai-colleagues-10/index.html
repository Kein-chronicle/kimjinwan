봇이 답하지 않을 때: 수신·실행·결과·송신을 나눠 확인하는 법

기록일 2026. 9. 4.수정 2026. 10. 13.

표시 날짜는 기존 운영 회고의 대표일입니다. 2026년 10월 14일 원본 기록을 대조하고 선톡·무응답 글을 통합했습니다.

이 글의 목적

메신저 봇의 무응답을 작업 실패·정상 억제·전송 미확인으로 나누고 재실행 전에 확인할 증거를 정한다.

핵심 내용

생성 능력과 송신 권한을 분리하고 수신·실행·결과·송신 기록을 같은 요청 ID로 연결한다.

읽고 나서

응답 없는 요청 하나의 마지막 성공 구간과 발송 억제 이유부터 기록한다.

한 줄 요약: 봇의 무응답은 수신·실행·결과·송신으로 나눠 확인하고, 먼저 보내는 메시지는 생성 전과 송신 직전에 허용 조건을 검사한다.

결과 파일은 생겼는데 채팅에는 아무 말도 오지 않을 수 있다. 반대로 타이머가 깨어났어도 보내지 않는 것이 올바른 동작일 수 있다. 두 경우를 “봇이 멈췄다”로 묶으면 불필요한 재실행이나 중복 발송을 만들기 쉽다. 이 글은 무응답의 마지막 성공 구간과 발송 억제 이유를 함께 기록하는 운영표를 제안한다.

개인 대화형 봇의 두 기록을 바탕으로 정리했다. 2026년 8월 17일에는 고정 문구 대신 생성 모델을 호출하는 경로가 추가됐고, 6월 7일 피드백에는 코드 수정 후 옛 프로세스가 계속 실행 중이었다는 진단이 있다. 10월 14일에는 코드 diff와 피드백 문서를 읽었으며 봇을 재시작하거나 시험 메시지를 보내지 않았다. 아래 운영표는 현재 구현 전체의 보증이 아닌 설계 제안이다.

아무 답도 없을 때 마지막 성공 구간을 찾는다

구간 확인할 증거 증거가 없을 때 다음 확인 바로 하면 곤란한 행동
수신 요청 ID와 접수 시각 전달 경로·수신 프로세스·대상 계정 같은 요청을 연속 전송
실행 요청 ID에 연결된 작업 ID·시작·종료 코드 대기열, 실행 중 프로세스, 잠금 살아 있는 작업을 새로 중복 실행
결과 생성 결과 파일 또는 레코드·내용 지문 실패 로그, 부분 결과, 저장 경로 빈 파일만 보고 완료 처리
송신 발송 요청 ID·응답 상태·상대 서비스의 메시지 ID 무음 정책, 발송 허용, 전송 오류 성공 여부 불명인데 무조건 재전송

각 구간의 기록은 같은 요청을 가리켜야 한다. 최근 결과 파일이 있다는 사실만으로 지금 요청이 끝났다고 판단하지 않는다. 요청 ID·작업 ID·결과 지문을 연결하면 어제 결과와 오늘 요청을 구분할 수 있다. 로그에 토큰이나 개인 대화 전문을 남길 필요는 없다.

송신 요청을 보냈지만 응답을 받기 전에 연결이 끊긴 경우가 특히 애매하다. 서버가 받았을 수도 있으므로 단순 재전송은 중복을 만들 수 있다. 이때는 “실패”와 “성공 여부 미확인”을 구분하고, 서비스가 제공하는 조회·중복 방지 수단을 확인한 뒤 재전송 정책을 정한다. 메시지 ID가 반환됐다는 사실도 상대 사람이 읽었다는 증거와는 다르다.

무음·일시 정지·취소는 다른 명령이다

이 글에서 제안하는 제어 의미는 다음과 같다. 실제 사용 중인 도구의 명령이 이 의미와 같은지는 해당 구현을 먼저 확인해야 한다.

제어 새 작업 접수 실행 중인 작업 외부 송신
무음 기존 정책 유지 계속 가능 차단
일시 정지 대기 또는 거절 중 하나로 정책 결정 계속·중단 중 하나를 명시 별도 정책 확인
작업 취소 해당 작업 ID에만 적용 취소 가능 지점에서 종료 취소된 결과 발송 차단
발송 허용 재개 기존 정책 유지 기존 정책 유지 아직 유효한 후보만 다시 판단

무음을 해제했다고 쌓인 알림을 전부 보내면, 이미 끝난 상황을 뒤늦게 전달할 수 있다. 후보마다 만료 시각을 두고 재개 시 다시 확인한다. “조용해져”라는 자연어 명령을 지원한다면 무엇이 차단됐고 무엇은 계속되는지 제어 결과에 명시한다. 내부 작업까지 멈췄다는 잘못된 기대를 만들지 않는 편이 낫다.

선톡은 문장 생성 전에 보낼 권한부터 본다

8월 17일 커밋 faf4f61의 텍스트 생성 함수는 만들어진 문장을 반환하고 직접 발송하지 않는 경로로 추가됐다. 발송 여부 검사 이후 생성 모델을 호출하고, 생성 결과에도 후보 검토를 적용하는 구조가 변경 기록과 diff에 있다. 이는 생성과 발송 결정을 분리한 코드 변경이다. 새 문장이 실제로 더 적절한 때 도착했는지는 별도 관찰이 필요하다.

먼저 보내는 기능에는 아래와 같은 허용표를 둘 수 있다. 항목은 이번 글의 운영 제안이며 그 커밋에 모두 구현됐다고 주장하는 목록이 아니다.

조건 억제 이유 코드 예 재검사 시점
사용자에게 먼저 연락할 허용이 없음 not_authorized 허용 변경 후
무음 또는 설정 편집 모드 muted / setting_mode 모드 변경 후
이전 메시지에 대한 답변을 기다림 waiting_reply 대기 조건 해소 후
최근 발송 간격 안에 있음 cooldown 기준 시각 이후
같은 후보를 이미 처리함 duplicate_candidate 새 후보 ID가 생겼을 때
후보가 오래돼 의미가 사라짐 expired_candidate 재전송하지 않고 새 상황 판단

생성 전에 조건을 검사하면 불필요한 생성 비용을 줄일 수 있다. 하지만 생성에 시간이 걸리는 동안 사용자가 무음으로 바꿀 수 있다. 따라서 송신 직전에 현재 권한과 모드를 다시 확인한다. 첫 검사 결과를 끝까지 재사용하지 않는다.

후보 하나가 생성 도중 무음으로 바뀌었다면

가상의 시간표로 경계를 살펴보자. 이는 실행 로그가 아니라 설계 예시다.

시각 사건 기대하는 처리
13:00:00 후보 C17, 현재 허용 생성 시작, 요청·후보 ID 기록
13:00:02 사용자가 무음 전환 현재 송신 정책 갱신
13:00:04 생성 결과 도착 현재 무음 재확인, 발송 억제 이유 기록
13:00:05 타이머가 같은 C17 다시 요청 동일 후보의 진행·종료 기록 확인
14:00:00 무음 해제 후보 유효기한 재확인, 무조건 재전송 금지

두 타이머가 동시에 같은 후보를 잡을 수 있다면 “보냈는지 조회 → 발송” 두 단계만으로 중복을 막기 어렵다. 둘 다 조회할 때 아직 미발송으로 볼 수 있기 때문이다. 후보를 한 실행자만 점유하도록 원자적인 저장 연산을 사용하고, 점유·발송 중·확인됨·미확인의 상태 전이를 기록하는 설계를 검토한다. 사용 중인 저장소가 지원하는 동시성 보장 범위와 외부 송신 결과를 함께 다뤄야 한다.

후보 ID만 추가했다고 정확히 한 번 발송이 보장되는 것은 아니다. 발송 후 기록 저장 전에 프로세스가 종료되는 경계가 남는다. 이때에도 성공 여부 미확인 상태를 보존하고 대조할 방법이 있어야 한다. 실패 재시도는 횟수·간격·기한을 정하고, 오래된 후보를 무한히 되살리지 않는다.

파일 수정과 실행 중인 버전도 분리한다

6월 7일 피드백은 데몬이 코드 수정 전 버전으로 실행 중이었다고 진단했고, 재시작 후 두 상태 필드의 저장을 확인했다고 보고했다. 이 글이 그 복구를 다시 실행한 것은 아니다. 이 기록의 교훈은 파일 저장 시각과 실행 프로세스의 버전이 다를 수 있다는 점이다.

따라서 복구 기록에는 변경한 코드 버전, 새 프로세스의 시작 시각, 처리한 시험 요청 ID, 결과 저장, 송신 결과를 따로 남긴다. 서비스가 켜졌다는 표시만으로 요청 처리가 정상이라는 결론을 내리지 않는다. 외부에 시험 메시지를 보낼 때는 허용된 대상과 내용을 정하고 실제 발송을 별도 작업으로 취급한다.

처음부터 재시작하지 말고 마지막 성공 구간부터 적는다. 기록이 부족하다면 그 부족함 자체를 먼저 보완한다. 표현이 반복되는 문제는 같은 입력 묶음으로 말투 비교, 오래된 상태가 들어오는 문제는 임시 상태 만료와 설정 이전에서 따로 다룬다.

세 줄 요약

  • 수신·실행·결과·송신을 같은 요청 ID로 연결하고 마지막으로 확인된 구간을 찾는다.
  • 선톡은 생성 전과 송신 직전에 허용 조건을 검사하며, 억제도 정상 처리 결과로 기록한다.
  • 송신 결과 미확인·중복 타이머·코드와 실행 버전 차이를 구분한 뒤 재시도와 복구를 결정한다.

  • 챗봇 말투가 반복될 때: 네 상황으로 비교하는 프롬프트 평가표
