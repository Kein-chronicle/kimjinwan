AI 활용기: 사진 가로세로가 거꾸로 측정된다: EXIF Orientation 때문에 PIL·sips 크기가 틀릴 때

발행 2026. 10. 5.
이 글의 목적

사진 가로·세로 판정이 뒤집히는 독자가 원인을 확인하고 표시 크기로 판정하도록 돕는다.

핵심 내용

Orientation 6 시험에서 저장 크기와 표시 크기의 가로·세로가 바뀌었고 5~8은 Django 티켓의 보고다. 표시 크기는 ImageOps.exif_transpose로 재고, 도구마다 다른 결과를 막으려면 회전을 픽셀에 굽고 태그를 없앤다.

읽고 나서

이미지 크기로 방향을 판정하는 코드가 있다면 시험 이미지를 하나 만들어 저장 크기와 표시 크기가 각각 무엇인지 먼저 출력해 본다.

먼저 답하면

사진의 size가 (400, 300)인데 화면에서는 세로 사진으로 보인다면, 파일에 EXIF Orientation 태그가 붙어 있을 수 있다. 이 시험에서 어긋남은 저장된 픽셀의 크기와 표시 크기가 달랐기 때문에 생겼다. Pillow의 Image.size와 sips의 pixelWidth·pixelHeight는 저장 크기를 알려 주었다. 표시 크기가 필요하면 ImageOps.exif_transpose(im).size로 재고, 파일을 넘겨 줄 때는 회전을 픽셀에 굽고 태그를 지운다.

증상: 가로로 통과시킨 사진이 실제로는 세로다

사진이 가로인지 세로인지 width > height로 판정하는 코드에서 이런 어긋남이 생길 수 있다. 이 글은 크롭이나 OCR 좌표는 시험하지 않았다. 도구마다 저장 크기를 보는지 표시 크기를 보는지가 달라 같은 파일에서 서로 다른 숫자가 나온다. 이 글은 그 차이를 작은 시험 이미지로 재현한다.

환경

macOS 26.6.2, Python 3.14.7, Pillow 12.2.0, Swift 6.4(AppKit·ImageIO)에서 2026년 10월 5일 실행했다. 다른 OS나 다른 Pillow 버전, 카메라 원본 파일은 시험하지 않았다.

시험 이미지 만들기

400x300 흰 이미지의 왼쪽 위에 빨간 사각형을 그리고 Orientation 6을 붙여 JPEG와 PNG로 저장한다. 그 뒤 도구별 크기를 출력한다.

import subprocess
from PIL import Image, ImageOps, ImageDraw

im = Image.new("RGB", (400, 300), "white")
ImageDraw.Draw(im).rectangle((0, 0, 99, 99), fill="red")
exif = Image.Exif(); exif[0x0112] = 6        # Orientation = 6
im.save("tagged.jpg", exif=exif); im.save("tagged.png", exif=exif)

for f in ("tagged.jpg", "tagged.png"):
    o = Image.open(f)
    print(f, "PIL size:", o.size, "| exif_transpose size:", ImageOps.exif_transpose(o).size)
    print(subprocess.run(["sips", "-g", "pixelWidth", "-g", "pixelHeight", "-g", "orientation", f],
                         capture_output=True, text=True).stdout)

fixed = ImageOps.exif_transpose(Image.open("tagged.jpg"))
fixed.save("baked.png")                      # 회전을 픽셀로 굽고 태그는 없다
o = Image.open("baked.png")
print("baked.png size:", o.size, "orientation tag:", o.getexif().get(0x0112))
print("baked.png sips:", subprocess.run(["sips", "-g", "pixelWidth", "-g", "pixelHeight", "baked.png"], capture_output=True, text=True).stdout.split())
print("baked.png 빨간 칸: 오른쪽 위(295,5) =", o.getpixel((295, 5)), "/ 왼쪽 위(5,5) =", o.getpixel((5, 5)))

Swift 쪽 측정은 아래 코드로 했다. swiftc로 컴파일해 세 파일을 인자로 준다.

import AppKit
import ImageIO
for f in CommandLine.arguments.dropFirst() {
  let u = URL(fileURLWithPath: f)
  let src = CGImageSourceCreateWithURL(u as CFURL, nil)!
  let p = CGImageSourceCopyPropertiesAtIndex(src, 0, nil)! as! [CFString: Any]
  let img = NSImage(contentsOf: u)!
  let cg = CGImageSourceCreateImageAtIndex(src, 0, nil)!
  print(f, "ImageIO PixelW x H:", p[kCGImagePropertyPixelWidth]!, p[kCGImagePropertyPixelHeight]!, "Orientation:", p[kCGImagePropertyOrientation] ?? "nil", "| CGImage:", cg.width, cg.height, "| NSImage.size:", img.size)
}

실제 결과

tagged.jpg PIL size: (400, 300) | exif_transpose size: (300, 400)
  sips: pixelWidth: 400 pixelHeight: 300 orientation: <nil>
tagged.png PIL size: (400, 300) | exif_transpose size: (300, 400)
  sips: pixelWidth: 400 pixelHeight: 300 orientation: <nil>
baked.png size: (300, 400) orientation tag: None
baked.png sips: ['baked.png', 'pixelWidth:', '300', 'pixelHeight:', '400']
baked.png 빨간 칸: 오른쪽 위(295,5) = (254, 0, 0) / 왼쪽 위(5,5) = (255, 255, 255)

본문 코드를 그대로 실행해 확인한 출력이며 sips 결과는 줄바꿈을 한 줄로 줄여 적었다. orientation 질의에는 <nil>이 나왔다.

macOS의 Swift에서 ImageIO와 NSImage로 같은 파일을 열었을 때는 다음과 같았다.

tagged.jpg ImageIO PixelW x H: 400 300 Orientation: 6 | CGImage: 400 300 | NSImage.size: (300.0, 400.0)
tagged.png ImageIO PixelW x H: 400 300 Orientation: 6 | CGImage: 400 300 | NSImage.size: (300.0, 400.0)
baked.png ImageIO PixelW x H: 300 400 Orientation: nil | CGImage: 300 400 | NSImage.size: (300.0, 400.0)

NSImage.size는 포인트 단위다. dpi는 측정하지 않았고 시험에서는 픽셀과 같은 숫자로 나왔다.

읽는 법: JPEG와 PNG 모두 Pillow size, sips, ImageIO의 픽셀 크기와 CGImage는 400x300이었고, exif_transpose 결과와 NSImage.size는 300x400이었다. 이 시험 이미지에서는 왼쪽 위 빨간 칸이 굽고 난 baked.png의 오른쪽 위(295, 5)에서 빨간색(JPEG 손실 때문으로 보이는 254, 0, 0)이 나왔다. 즉 Orientation 6은 표시할 때 시계 방향 90도로 돌리라는 뜻으로 작동했다. 굽고 난 파일은 시험한 다섯 가지 측정(Pillow, sips, ImageIO, CGImage, NSImage) 모두에서 300x400으로 같았다.

원인

Pillow 공식 문서는 exif_transpose가 Orientation 태그가 1이 아닐 때 이미지를 그에 맞게 변환하고 방향 정보를 제거한다고 설명한다. 반대로 Image.open().size는 저장된 픽셀 크기다. Django 티켓 #34035에는 Orientation 5~8인 이미지의 너비·높이가 서로 바뀌어 저장된다는 보고가 있고, 해당 티켓은 wontfix로 닫혔다. 티켓 보고자는 Pillow가 EXIF 회전을 일부러 무시한다고 설명한다. 한 저자의 메모는 Pillow로 열고 저장한 사진이 회전되는 사례를 보여 준다. 해결로 exif_transpose를 쓴다.

해결 절차

  1. 방향 판정과 크기 규격 검사는 ImageOps.exif_transpose(im).size 같은 표시 크기로 한다. im.size만 믿지 않는다.
  2. 파일을 저장하거나 다른 도구에 넘길 때는 exif_transpose 결과를 저장한다. 시험에서 이렇게 하면 태그가 없어지고 시험한 다섯 가지 측정이 300x400으로 일치했다.
  3. 태그를 남긴 채 저장하려면 exif=로 명시해야 한다. 이 경우 위 도구별 불일치가 남을 것으로 추정하지만 이 방식은 시험하지 않았다.

확인 방법과 안 되는 경우

먼저 getexif().get(0x0112)로 태그 값을, ImageOps.exif_transpose(im).size로 표시 크기를 출력한다. 두 크기의 가로·세로가 서로 다르면 이 글의 경우다. 이 시험은 Orientation 6만 다뤘다. 태그가 없는데도 방향이 이상하다면 원본 픽셀이 실제로 눕혀 있거나 다른 도구가 태그만 지운 경우처럼 다른 원인이 있다. 그때는 원인을 확인하고, 돌려서 규격을 맞추지 않는다. 가로 규격을 통과시키려고 세로 화면을 눕히면 검사를 속이게 되므로 실패로 남기는 편이 맞다.

이 글은 시험 이미지 한 장의 Orientation 6만 확인했다. 다른 값(2~5, 7, 8)의 거울 반전 조합이나 카메라 원본, 다른 라이브러리는 시험하지 않았다. sips에서 방향 태그 값을 직접 읽는 방법도 확인하지 못했다. 태그가 있는지는 Pillow의 getexif()나 ImageIO의 Orientation 속성으로 본다.

같이 읽을 글

  • set -e 스크립트가 에러 없이 중간에 끝날 때: 변수에 담은 grep 한 줄 찾기

    set -e를 켠 bash 검사 스크립트가 통과해야 할 때만 아무 메시지 없이 멈췄다. macOS bash 3.2·zsh·sh로 원인(grep의 매치 없음 종료 코드 1)과 세 가지 수정, 수정이 삼키는 오류를 재현했다.

  • SwiftUI 공유 시트가 비어 있을 때: item으로 공유 데이터 함께 넘기기

    첫 공유가 빈 시트인 경우를 자체 예제로 대조하고, 선택한 문자열과 Copy 출력까지 확인하는 item 기반 구현을 제공한다.

  • SwiftUI 숫자패드 닫기: 두 입력칸의 포커스를 nil로 해제하기

    numberPad·decimalPad 화면에 Done 버튼을 추가하고, 두 입력칸에서 버튼 한 개·키보드 닫힘·입력값 보존을 확인하는 최소 예제를 제공한다.
