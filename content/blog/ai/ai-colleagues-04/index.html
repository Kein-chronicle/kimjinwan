챗봇이 끝난 일을 계속 말할 때: 기억·임시 상태·설정 이전을 나누는 법

기록일 2026. 5. 22.수정 2026. 10. 13.

표시 날짜는 초기 설계의 대표 기록일입니다. 2026년 10월 14일에 5월 코드 기록을 다시 확인하고 기억·만료·설정 이전 글을 통합했습니다.

이 글의 목적

대화형 캐릭터의 오래된 상황이 새 답변에 섞일 때 어느 저장 계층을 점검할지 판단한다.

핵심 내용

상태의 값뿐 아니라 관측 시각·유효기한·해제 사건·설정 버전을 함께 관리하고, 장기 기억을 현재 상태처럼 주입하지 않는다.

읽고 나서

반복되는 문장 하나를 골라 원본 기억, 현재 상태, 생성 입력 중 어디에서 들어왔는지 추적한다.

한 줄 요약: 챗봇이 끝난 일을 계속 말한다면 기억·현재 상태·실행 모드를 나누고, 각 상태에 유효기한과 해제 사건을 함께 적는다.

어제의 식사나 이전 캐릭터 설정이 오늘 답변에 끼어들 때, 프롬프트에 “기억을 잘해”라고 한 줄 더 쓰는 것으로는 원인을 찾기 어렵다. 어디에 남은 정보가 어떤 경로로 답변에 들어왔는지 먼저 나눠야 한다. 이 글은 저장 계층별 점검표와 설정을 바꿀 때 사용할 이전 절차를 제안한다.

개인 대화형 캐릭터 프로젝트의 2026년 5월 기록을 10월 14일에 다시 읽었다. 아래 날짜는 코드와 문서의 변경일이다. 당시 대화를 재생하거나 답변 품질을 새로 측정한 결과는 아니다. 실제 이용자의 대화 대신 가상의 시간과 활동으로 예시를 구성했다.

같은 문장도 저장 위치에 따라 뜻이 다르다

“점심을 먹고 있다”를 장기 기억에 저장하면 다음 날에도 검색될 수 있다. 과거 대화 이력이라면 맞는 기록이지만, 현재 상태로 넣으면 잘못된 답변 재료가 된다. 기억을 지울지 고민하기 전에 과거 사실을 보존할 장소와 지금 유효한 값의 장소를 구분한다.

계층 저장할 내용 바뀌는 계기 답변에 넣기 전 확인
프로필 가상 인물의 역할·말투·설정 버전 명시적 설정 변경 현재 버전과 맞는가
장기 기억 과거에 나눈 약속·선호와 그 출처 정정·철회·보존 기간 종료 과거 일인지, 지금도 유효한 선호인지
임시 상태 활동·바쁨·현재 장면 시간이 지남, 활동 전환, 취소 관측 시각·만료·해제 사건
실행 모드 대화 허용, 설정 편집, 송신 허용 사용자의 모드 전환 이번 행동에 권한이 있는가
파생 정보 요약·검색 캐시·이미지용 상황 원본이나 설정 버전 변경 원본과 같은 버전을 참조하는가

이 표는 이번 글에서 제안하는 분류다. 기존 시스템에 이 다섯 계층과 버전 검사가 모두 구현됐다는 뜻은 아니다. 같은 저장 파일을 쓰더라도 용도와 갱신 책임을 분리할 수 있다.

5월 코드에서 확인한 세 가지 변경

5월 23일 커밋 2f9cc8d의 tools/automation_worker.py에는 활동별로 허용하는 식사 필드 집합이 있다. 현재 활동에서 쓰지 않는 meal_phase, meal_status_note, dinner_mode, dinner_menu_hint를 presence.pop으로 제거한다. 따라서 식사 필드 정리는 5월 23일 코드에 이미 있다. 5월 26일 변경의 성과로 옮겨 적으면 날짜 귀속이 틀린다.

5월 26일 커밋 69a3942는 check_counterpart_block_expiry를 추가한다. 바쁨 제한을 끝내는 기준은 둘이다. 지정된 시각을 지났는지 확인하거나, 점심·퇴근·기상 같은 활동 전환과 제한 종류를 대조한다. 예를 들어 점심 전환은 업무 제한을, 기상 전환은 수면 제한을 해제하도록 되어 있다. 이는 바쁨 상태에 만료 기능을 추가한 기록이다. 식사 필드와 같은 장애를 고쳤다는 증거로 읽을 수는 없다.

5월 29일 d6cea02에서는 프로필과 생활 일정을 함께 바꾸고, 5월 30일 2718889에서는 존재 방식과 활성화 점검 문서를 수정했다. 이어 45917f1은 타이머와 실행 코드의 일정·이미지 문맥도 바꿨다. 설정 변경이 소개문 한 곳에만 머물지 않았다는 기록이다. 이들 변경만으로 실제 답변에서 이전 설정이 모두 사라졌다고 판정할 수는 없다.

기록에서 배울 점 바로 적용할 질문 여기서 알 수 없는 것
활동별 식사 필드 제거 새 활동에 필요 없는 이전 필드가 남는가 자연스러운 답변이 얼마나 늘었는가
시각·활동 기준 바쁨 해제 해제 시각과 해제 사건이 둘 다 정의됐는가 모든 자정·중복 사건 경계가 안전한가
프로필·일정·타이머 연쇄 수정 새 설정을 읽는 모든 입력을 찾았는가 각 참조가 운영 중 실제 갱신됐는가

임시 상태 한 건에 붙일 최소 정보

다음은 구현을 위한 설계 예시다. 실제 프로젝트의 저장 형식을 복사한 것이 아니다. 시간은 날짜와 시간대를 포함하고, “확인하지 못함”을 “현재 자유로움”과 구분한다.

{
  "value": "busy",
  "observed_at": "2026-10-14T13:00:00+09:00",
  "valid_until": "2026-10-14T14:00:00+09:00",
  "clear_on": ["meeting_finished", "cancelled"],
  "source": "explicit_input",
  "profile_version": 3
}

판정 순서는 설정 버전 확인 → 최신 정정·취소 확인 → 만료 시각 확인 → 현재 값 선택이다. 유효기한이 지난 정보는 현재 상태 입력에서 제외하고, 필요하면 과거 이력으로 남긴다. 만료됐다는 이유만으로 반대 상태가 참이 되는 것은 아니다. 회의가 14시에 끝날 예정이었다고 해서 그 시각에 실제로 한가해졌다고 추정하지 않는다.

자정을 넘는 약속을 다루면 HH:MM만 비교해서는 날짜를 구분할 수 없다. 5월 26일 코드의 시각 비교는 시·분을 분으로 환산하는 방식이므로, 위 날짜 포함 형식은 그 코드를 그대로 재현한 것이 아니라 개선 제안이다. 단말과 서버 시간이 어긋날 수 있다면 관측 주체와 기준 시간도 정해야 한다.

가상 입력 점검할 경계 기대하는 설계 결과
13:59:59에 바쁨 조회 만료 직전 유효한 바쁨 상태 유지
14:00:00에 조회 만료와 같은 시각 현재 값에서 제외, 실제 활동은 미확인
13:30에 회의 취소 시간보다 빠른 해제 사건 바쁨 상태 해제
같은 취소 사건이 두 번 옴 중복 처리 두 번째 처리가 새 알림을 만들지 않음
전날 23:50 시작, 다음 날 00:10 만료 날짜 경계 같은 날 시·분만으로 조기 해제하지 않음
프로필 4인데 상태는 버전 3 설정 교체 오래된 상태를 생성 입력에서 격리

이 표는 회귀 시험의 입력과 기대값이며 실행 결과표가 아니다. 시간을 고정할 수 있는 시험 환경에서 상태 선택 결과와 실제 생성 입력을 각각 기록해야 한다. 상태 계산이 맞는데 답변이 틀리면 저장소보다 입력 조립·모델 응답 쪽을 살펴본다.

캐릭터 설정을 바꿀 때는 참조 목록부터 만든다

프로필만 바꾸고 일정·요약·캐시를 그대로 두면 서로 다른 버전이 한 답변에 섞일 수 있다. 이를 예방하려면 변경 전후의 입력을 비교할 수 있어야 한다. 아래는 이번 글의 이전 절차 제안이다.

  1. 새 설정에 버전을 붙이고 이전 프로필과 대응표를 보관한다. 예: 외부 출근 설정을 실내 작업 설정으로 바꿀 때 없어지는 활동 키를 적는다.
  2. 그 키를 참조하는 일정, 타이머, 상태 요약, 이미지 문맥, 먼저 보내는 메시지 규칙을 찾는다. 자연어 표현과 코드 키를 함께 찾는다.
  3. 각 항목에 유지·재생성·격리를 정한다. 과거 이력은 당시 사실로 보존할 수 있지만 현재 생성 입력에 자동으로 합치지 않는다.
  4. 설정 편집 모드에서 새 입력 묶음을 만든 뒤 가상 질문을 비교한다. “지금 어디야?”, “다음 일정은?”, “어제 하던 일은?”의 답변 근거를 각각 기록한다.
  5. 새 버전의 입력과 송신 직전 상태를 확인하고 대화 모드로 전환한다. 실패하면 이전 버전의 프로필과 파생 입력을 함께 복구한다.

프롬프트에 “옛 설정을 잊어라”라고 쓰는 것은 지시다. 저장된 요약·대기열·캐시를 실제로 지운 기록과 다르다. 삭제 여부는 파일·레코드에서, 답변에 쓰였는지는 생성 입력에서 확인한다. 모드 분리도 마찬가지다. 대화가 설정 변경을 제안하는 것과 파일 수정 권한을 얻는 것을 별도로 취급한다.

다음에 같은 문장이 나오면 남길 한 줄

발생 시각 | 답변 문장 | 유입 계층 | 원본 버전 | 관측 시각 | 만료/해제 조건 | 실제 생성 입력 포함 여부

이 한 줄이 있으면 기억 전체를 지우는 대신 오래된 정보가 통과한 위치를 좁힐 수 있다. 처음에는 문제 문장 하나면 충분하다. 개인 대화 전문을 보고서에 복사하지 말고, 필요한 상태 키와 가상의 대체 문장으로 재현한다. 기록을 남길 때도 보존 기간과 접근 범위를 정한다.

기억을 많이 남기는 것보다, 지금 답변에 써도 되는 기억을 구분하는 일이 먼저다. 관련 글의 실행·검토 완료 구분은 AI 코드 리뷰 적용 점검에서 이어 볼 수 있다.

세 줄 요약

  • 프로필·과거 기억·임시 상태·실행 모드·파생 정보를 나눠 오래된 문장의 유입 경로를 찾는다.
  • 만료 시각과 해제 사건을 함께 기록하되, 만료를 반대 상태의 확정으로 해석하지 않는다.
  • 설정 이전 때는 소개문뿐 아니라 일정·요약·캐시의 참조 버전과 실제 생성 입력을 확인한다.

  • AI가 쓴 코드 리뷰를 그대로 적용해도 될까: 적용 전에 확인할 4가지

    AI가 쓴 리뷰 두 건과 적용 기록을 읽었다. 한 건은 이미 고쳐진 오류를 원인으로 짚었다. 로그와 코드 수정일 비교, 지적-코드-재현-결정 비교표를 정리했다.
