AI가 쓴 코드 리뷰를 그대로 적용해도 될까: 적용 전에 확인할 4가지

기록일 2026. 6. 8.수정 2026. 10. 14.

표시 날짜는 이 글이 다루는 작업의 대표 기록일이며, 당시 발행된 글을 뜻하지 않습니다. 이후 회고와 적용 방법은 2026년 9월에 정리했습니다.

이 글의 목적

AI가 쓴 코드 리뷰나 감사 문서를 받아 적용하려는 개발자가, 지적을 그대로 따르지 않고 현재 코드·로그 날짜·재현 여부를 먼저 확인하도록 돕는다.

핵심 내용

AI 리뷰는 리뷰가 본 버전과 현재 코드를 대조한 뒤 적용한다. 오류 로그는 마지막 수정 시각을 코드 수정 시각과 비교해 이미 지난 오류인지 가르고, 지적·현재 코드·재현 여부·결정을 한 줄씩 남긴다.

읽고 나서

지금 받아 둔 AI 리뷰의 지적 하나를 골라 비교표 한 줄을 채워 본다. 먼저 근거로 든 로그 파일의 수정일과 해당 코드의 수정일을 ls -l 로 나란히 확인한다.

한 줄 요약: AI가 쓴 코드 리뷰는 지적 하나마다 현재 코드·로그 날짜·재현 여부를 확인한 뒤 적용해야 하며, 2026년 6월의 리뷰 두 건 중 하나는 이미 고쳐진 오류를 원인으로 짚었다.

AI에게 코드 리뷰를 받으면 지적 목록이 길고 그럴듯하다. 그래서 위에서부터 그대로 고치고 싶어진다. 이 글은 개인 프로젝트에서 AI가 쓴 리뷰 문서 두 건과 그 적용 기록을 읽은 기록이다. 첫 건은 코드 위치와 수정 방향이 구체적으로 적혀 있었고, 둘째 건은 지적한 오류가 이미 고쳐진 뒤의 것이었다. 두 사례에서 뽑은 점검 4가지, 역할별 완료 증거, 지적-현재 코드-재현-적용 여부를 한 줄씩 적는 비교표를 함께 둔다.

먼저 용어다. 요카이는 리뷰 문서를 받아 코드에 적용하는 AI다. 웅삐는 사진과 대화를 주고받는 채팅 챗봇 캐릭터 프로젝트이고, 웨일 서바이버는 게임 프로젝트다. 둘 다 개인 프로젝트다. 리뷰 문서는 인계 폴더(폴더 이름은 fairy)에 파일로 넘기는데, 폴더 안내문은 이를 다른 작업 세션이나 모델에게 넘기는 검토 결과라고 설명한다. 적용한 쪽이 제안과 다르게 처리한 항목이 있으면 같은 이름의 피드백 파일로 이유와 함께 돌려준다. 이 폴더의 운영 규칙은 인계 문서를 수정 방향 제안서로 보고, 구현 가능성과 충돌 여부를 다시 확인한 뒤 적용하라고 정해 둔다.

코드 위치와 수정 방향이 적힌 리뷰: 게임 설계와 구현의 어긋남

2026-06-04에 쓴 리뷰는 웨일 서바이버 1막 시작 고래(외뿔고래)의 구현을 설계 문서와 대조했다. 기준은 브랜치 meta-unlock의 커밋 89bfc7fb였고, 설계 문서가 정한 값은 시작 무기 슬롯 2칸, 초기 공용 카드 6장, 레벨업 선택지 2장, 슬롯이 다 찰 때까지 신규 무기 우선이었다. 리뷰는 구현이 일부만 맞고 범위와 적용 위치가 계획과 어긋난다고 보았고, 가장 큰 문제 셋을 코드 위치와 함께 적었다.

지적 리뷰가 든 코드 근거 적용 전에 확인할 질문
1막 전용 규칙이 외뿔고래 전체 규칙으로 들어감 고래 종류만 보고 슬롯 2·선택지 2를 정하는 삼항 연산 두 곳 2막 이상에서도 같은 값이 적용되는가
초기 카드 6장이 실제로는 9장으로 불어남 스타터 덱 생성 함수가 카드 상한 9장까지 다른 카드로 채움 전투 시작 시점의 실제 후보 수는 몇 장인가
신규 무기 우선이 단순 가중치 3배 신규 무기 후보를 3번 반복해 넣는 코드 운이 나쁘면 강화 카드만 2장 나오는 경우가 남는가

이 세 지적은 모두 “코드에 이름이 있다”와 “그 규칙이 실제 선택을 지배한다”의 차이를 짚는다. 리뷰의 요지는 상수 6장이 코드에 있어도 덱을 만드는 함수가 다시 9장으로 채우면 6장 규칙이 실제로는 쓰이지 않는다는 것이다. 리뷰는 수정 방향도 제안했다. 세 번째 지적에는 결과 카드 2장을 정하기 전에 신규 무기 후보 1장을 먼저 뽑고 나머지 1장만 일반 규칙으로 채우라고 했다. 가중치를 올리는 것만으로는 “우선”은 되어도 “신규 무기가 남았는데 강화 카드만 나오는 상태 방지”는 보장되지 않기 때문이다.

이 사례의 교훈은 리뷰를 받을 때 함수 이름을 찾아 달라고 하지 말고 “이 조건이 실제 선택 경로를 지배하는가” 같은 질문으로 맡겨야 한다는 것이다. 이 리뷰는 코드 위치 옆에 “수정 방향”과 “추천 수정 위치”를 같이 적어 두어, 적용하는 쪽이 지적을 코드에서 찾아 확인할 수 있는 형식이다. 다만 이 글은 당시 리뷰 문서를 읽은 기록이며, 지적이 모두 맞았는지, 지금 코드에 같은 문제가 남아 있는지는 확인하지 못했다. 게임 저장소는 현재 원래 경로에 없어 코드를 다시 열 수 없었고, 이 리뷰에 대한 적용 피드백 문서는 찾지 못했다.

리뷰가 이미 지난 오류를 짚은 경우: 사진이 안 나간 날

2026-06-08에는 웅삐의 사진 요청이 한동안 실패했다. 저녁 8시 35분부터 8시 58분 사이에 사용자가 사진을 세 번 요청했고, 챗봇은 “사진이 바로 안 붙네” 같은 텍스트만 보냈다. 그날 마지막으로 생성된 이미지는 오후 7시 27분 것이었고, 요청이 시작된 8시 35분 이후에는 새 이미지 파일이 없었다. 리뷰는 원인을 이렇게 봤다. 워커 프로그램의 오류 로그에 TypeError: argument of type 'NoneType' is not iterable이 있고, 장면 요약이 비어 있는 채로 문자열 검사를 해서 워커가 죽었다는 것이다. 수정 방향은 비어 있는 값을 빈 문자열이나 빈 사전으로 바꾸는 방어 코드였다.

요카이가 현재 코드를 열자 그 방어는 이미 있었다. 장면 요약을 읽는 줄에 or ""가 붙어 있었다. 결정적인 단서는 날짜였다. 오류 로그 파일의 마지막 수정일은 5월 30일이었고, 워커 코드의 마지막 수정일은 6월 8일 오전 7시 6분이었다. 로그의 오류는 코드가 고쳐지기 전에 남은 것이었다.

항목 리뷰가 본 것 현재 코드·파일로 확인한 것
원인으로 지목한 오류 로그의 NoneType 오류 로그 수정일 5월 30일, 코드 수정일 6월 8일. 해당 줄에는 이미 or ""
두 번째 오류 NameError: TOOLS 현재 코드가 TOOLS를 불러오고 있고 검사 스크립트 파일도 존재
실제 원인 언급 없음 워커 프롬프트 안의 사진 전송 점검 명령 4곳이 옛 위치(데스크톱 폴더)를 가리킴

실제 원인은 프로젝트를 데스크톱 폴더에서 프로젝트 폴더로 옮기면서 남은 고정 경로였다. 워커에게 주는 지시문의 1단계(스냅샷)와 3단계(전송 점검)가 옛 경로의 스크립트를 실행하게 되어 있었고, 1단계가 실패하자 이미지 생성 도구를 아예 부르지 않았다. 요카이는 네 곳을 새 경로로 고치고 세션 ID를 초기화해 다음 요청부터 적용되게 했다. 이 설명은 피드백 문서가 기록한 내용이며, 이 글에서 장애를 다시 재현한 것은 아니다.

리뷰의 다른 제안(실패 유형을 코드로 나눠 기록하기, 같은 핑계 문장 반복하지 않기)은 “현재 동작에 큰 문제 없어 보인다”는 이유로 보류됐다. 피드백은 남는 위험도 적었다. 장면 요약 함수가 활동을 목록에서 못 찾으면 None을 돌려주는 구조는 그대로라서, 새 호출부를 추가할 때 주의해야 한다.

적용 전에 확인할 4가지

두 사례에서 공통으로 쓸 수 있는 순서다.

  1. 버전을 고정한다. 리뷰가 어느 커밋을 봤는지 적혀 있는지 확인한다. 첫 사례의 리뷰는 브랜치와 커밋을 적어 두어 어느 코드를 본 것인지 알 수 있다.
  2. 로그는 날짜부터 본다. 오류 로그의 마지막 수정 시각이 문제의 코드를 고친 시각보다 앞서면 그 오류는 과거 것일 수 있다. ls -l이나 stat으로 두 파일의 시각을 나란히 본다. 로그가 더 오래됐다는 사실이 오류가 고쳐졌다는 증명은 아니므로, 해당 줄을 직접 열어 확인한다.
  3. 파일과 실행 중인 프로그램을 구분한다(두 사례 밖의 일반 점검이다). 코드가 최신이어도 돌고 있는 프로세스가 옛 코드를 읽고 있을 수 있다. 재시작은 진행 중인 작업을 끊을 수 있으므로 적용 여부와 별도로 판단한다.
  4. 지적을 재현 가능한 질문으로 바꾼다. “None 방어를 추가하라”보다 “사진 요청 시 장면 요약이 비면 어떻게 되는가”가 낫다. 정상 조건 하나와 경계 조건 하나를 함께 시험한다. 코드만 읽고 내린 결론과 실제 입력으로 실행한 결과는 표에서 다르게 표시한다.

실행 담당과 검토 담당의 완료 증거를 나눈다

역할을 나눌 때 이름이나 말투보다 먼저 정할 것은 권한과 제출물이다. 아래 표는 앞선 기록을 바탕으로 만든 운영 제안이다. 당시 구현에 이미 이 검사가 모두 있었다는 뜻은 아니다.

역할 허용할 행동 완료로 받는 증거 끝났다고 오해하기 쉬운 상태
실행 담당 정해진 파일 수정과 허용된 시험 기준 버전, 변경 목록, 실행 명령과 종료 결과, 남은 실패 파일만 고치고 실행 중인 프로세스 반영을 확인하지 않음
독립 검토 담당 원고·코드·로그 읽기, 재현 질문과 반례 제시 검토한 버전, 주장별 근거 위치, 확인·미확인 구분 긴 지적 목록을 냈지만 옛 로그를 현재 장애로 읽음
적용 판단 담당 지적별 채택·보류·기각 결정 실제 변경과 다르게 처리한 이유, 다시 확인할 조건 검토 문서가 통과했으니 모든 수정을 적용했다고 보고함

작은 프로젝트에서는 한 사람이 여러 역할을 맡아도 된다. 다만 검토 단계에서는 수정 권한을 잠시 분리하고, 실행한 쪽의 “통과” 문장을 답안처럼 먼저 보여 주지 않는 편이 좋다. 별도 AI 세션을 쓰더라도 같은 가정을 공유할 수 있으므로, 서로 다른 이름이 독립 검증의 증거가 되지는 않는다.

복사해서 쓸 요청은 짧게 만들 수 있다. “커밋 A의 변경을 읽기 전용으로 검토하고, 문제마다 해당 줄·발생 입력·기대 결과·확인하지 못한 것을 적어라. 파일은 수정하지 말라.” 실행 담당에게 넘길 때는 각 지적의 적용 여부를 따로 적는다. 검토가 끝난 시점과 수정이 실제 반영된 시점은 다른 상태다.

“재현하지 못했다”는 칸은 비워 두지 말고 미재현이라고 적는다. 그래야 다음 리뷰어가 같은 지적을 반복하지 않고, 아직 남은 불확실성도 알 수 있다. 제안과 다르게 처리한 항목에는 이유와 남는 위험을 같이 남긴다. 둘째 사례에서 오류의 시점을 판단할 수 있었던 것도 그 기록 덕분이다. 근거로 읽은 문서는 인계 폴더의 네 건이다: 2026-06-04 웨일 서바이버 구현 감사, 2026-06-08 사진 요청 실패 감사와 그 적용 피드백, 폴더 운영 규칙.

세 줄 요약

  • AI 리뷰는 지적마다 리뷰가 본 버전과 현재 코드를 대조한 뒤 적용한다.
  • 오류 로그는 마지막 수정 시각을 코드 수정 시각과 비교해 이미 지난 오류인지 먼저 가른다.
  • 지적·현재 코드·재현 여부·적용 결정을 한 줄씩 남기면 다음 리뷰어가 같은 지적을 반복하지 않는다.

같이 읽을 글

  • 봇이 답하지 않을 때: 수신·실행·결과·송신을 나눠 확인하는 법

    무응답의 마지막 성공 구간과 선톡 억제 이유를 기록한다. 생성 도중 무음 전환, 중복 타이머, 송신 결과 미확인에 대한 운영표.

  • AI 동료 제작기: 사진을 만들었는데 대화에는 도착하지 않았다

    생성 성공과 전송 성공, 상황의 일관성은 달랐다. 사진과 음성을 붙이며 늘어난 확인 항목들.

  • 챗봇 말투가 반복될 때: 네 상황으로 비교하는 프롬프트 평가표

    확인·설명·바쁨·거절 입력으로 말투 변경을 비교한다. 질문·길이·반복 표현과 내용 오류를 나누고, 구현 확인을 효과 측정과 구분하는 기록 양식.
