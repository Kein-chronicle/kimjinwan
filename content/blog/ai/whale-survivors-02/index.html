웹게임 iOS 포팅 점검: 번들·광고 복귀·심사 제출의 증거

기록일 2026. 4. 22.수정 2026. 10. 13.

표시 날짜는 기존 초기 포팅 글의 대표일입니다. 2026년 10월 14일 후대 Capacitor 소스와 8월 제출 문서를 확인해 02·10을 통합했습니다.

이 글의 목적

웹게임을 iOS 앱으로 묶는 개발자가 번들·네이티브 광고·제출 단계마다 필요한 증거를 구분한다.

핵심 내용

화면이 뜬 것, 광고를 닫은 것, 빌드를 업로드한 것은 서로 다른 상태다. 번들 식별과 보상 이벤트, 제출 상태를 각각 기록한다.

읽고 나서

설치 앱의 번들 식별값과 광고 요청별 결과를 남기고 업로드·처리·심사 제출 상태를 별도 칸에 적는다.

연재 목차

  3. 게임 이미지 검수와 용량 감사: 카드·액션·파일·프레임을 나누는 법
목차
  • 첫 화면보다 먼저, 앱 안의 번들을 식별한다
  • 광고를 닫았다는 이벤트로 보상을 지급하지 않는다
  • 브라우저 스크린샷은 네이티브 광고의 증거가 아니다
  • 업로드·심사 제출·승인을 따로 기록한다
  • 세 줄 요약

한 줄 요약: 웹게임의 iOS 포팅은 웹 번들 반영, 네이티브 기능 복귀, 스토어 제출 상태를 각각 다른 증거로 확인해야 한다.

웹 브라우저에서 게임이 실행됐고 아이폰 모양의 스크린샷도 있다. 여기서 “iOS 앱 준비 완료”를 체크하면 두 가지가 빠진다. 앱에 어느 웹 번들이 들어갔는지, 광고를 닫고 어떤 결과로 게임에 돌아왔는지다. 업로드에 성공했더라도 심사 승인은 또 다른 상태다.

웨일서바이버의 보관 소스와 2026년 8월 제출 기록을 읽어, 이 경계를 점검하는 방법을 정리했다. 초기 SwiftUI 구현의 원본 경로는 이번 확인에서 찾지 못했다. 아래 코드 분석은 회수한 후대의 Capacitor 앱을 대상으로 한다. 실제 기기나 App Store Connect에서 새로 실행·제출한 결과는 아니다.

첫 화면보다 먼저, 앱 안의 번들을 식별한다

회수한 capacitor.config.ts에는 webDir: "dist"가 있다. package.json의 mobile:sync는 npm run build && cap sync다. 웹 소스를 빌드한 다음 그 결과를 네이티브 프로젝트에 반영하는 순서다. 웹 소스만 수정했거나, 빌드만 하고 동기화를 생략했다면 브라우저와 앱이 서로 다른 파일을 실행할 수 있다.

Capacitor의 작업 흐름 문서도 웹 빌드 뒤 sync로 번들과 네이티브 의존성을 반영하고 네이티브 프로젝트를 실행하는 순서를 설명한다. 보관 프로젝트의 Capacitor 주 버전은 7이므로, 현재 문서를 읽었다는 이유로 의존성을 바꾸거나 당시 빌드 결과를 재현했다고 보지는 않았다.

다음은 이 소스에서 출발한 검사 제안이다. 통과 기록이 아니라 직접 남겨야 할 증거 목록이다.

경계 남길 증거 실패했을 때 먼저 볼 곳
웹 소스 → dist 소스 커밋, 빌드 시각, 번들 파일 목록이나 해시 빌드 명령과 실제 출력 폴더
dist → iOS 프로젝트 동기화 로그, 복사된 대표 파일의 해시 webDir와 동기화 실행 여부
iOS 프로젝트 → 실행 앱 버전·빌드 번호와 게임 안의 별도 번들 식별값 설치한 앱이 이번 산출물인지
실행 앱 → 광고 → 게임 요청 위치, 보상·닫힘·실패 이벤트, 복귀 뒤 게임 상태 네이티브 어댑터와 게임 보상 처리

예를 들어 버튼 문구를 A에서 B로 바꿨는데 앱에는 A가 남아 있다면 광고 SDK부터 의심할 필요는 없다. dist에 B가 있는지, 동기화된 파일에도 B가 있는지, 그 파일로 만든 앱을 설치했는지 순서대로 좁힌다. 번들 식별값은 새로 추가할 관측 장치다. 당시 게임에 이미 있었다는 뜻은 아니다.

광고를 닫았다는 이벤트로 보상을 지급하지 않는다

보관된 admobAdapter.ts는 Rewarded 이벤트가 오면 이번 노출의 보상 표식을 켠다. Dismissed는 대기를 풀지만 보상 표식을 켜지 않는다. FailedToShow는 실패 표식과 대기 해제를 처리한다. 결과도 rewarded, dismissed, error, unavailable로 나뉜다.

이 구분은 “광고 창에서 돌아왔다”는 사실과 “보상 조건을 충족했다”는 사실을 분리하기 위한 것이다. Google의 iOS 보상형 광고 안내도 보상 콜백과 전체 화면 닫힘 콜백을 별도로 다룬다. 중개 광고의 콜백 순서는 연결된 SDK에 따라 달라질 수 있으므로, 임의의 대기 시간만으로 모든 순서를 해결했다고 결론 내릴 수 없다.

관측한 사건 코드에서 구분하는 결과 게임 쪽에서 따로 확인할 것
광고 준비 실패 또는 로드 시간 초과 unavailable 대기 표시 해제, 재시도 가능 여부
보상 표식 없이 광고를 닫음 dismissed 재화나 부활을 지급하지 않는지
표시 실패 이벤트 보상 표식이 없다면 error 게임이 입력을 다시 받는지
이번 노출의 보상 이벤트 rewarded 해당 요청에 보상을 정확히 한 번 적용하는지

코드에는 준비 대기 상한 10초와 보상 신호 추가 대기 250밀리초가 있다. 이는 이 프로젝트의 구현값이다. 모든 네트워크·중개 광고에 적합한 권장값은 아니다. 특히 “한 번만 지급”은 반환 문자열만 보고 입증할 수 없다. 게임의 지급 로직과 중복 요청 처리까지 함께 검사해야 한다.

검사 로그는 다음처럼 요청과 결과를 연결해 남기는 편이 좋다. 아래는 제안 형식이며 실제 광고 로그가 아니다.

request_id=example-17 placement=revive
prepare=success
reward_event=false dismiss_event=true
outcome=dismissed grant_count=0 input_resumed=true

성공 경로만 보지 말고 조기 닫기, 준비 실패, 표시 실패, 연속 누르기를 각각 실행한다. 실제 광고를 누르며 시험하는 대신 SDK가 안내하는 테스트 광고로 검증한다. 이 글에서는 해당 실기기 검사를 수행하지 않았다.

브라우저 스크린샷은 네이티브 광고의 증거가 아니다

같은 파일의 registerAdMobIfNative()는 네이티브 플랫폼이 아니면 즉시 반환한다. 보관된 스토어 README도 브라우저 캡처에는 실제 광고가 없고, 배너 자리표는 캡처 직전에 숨긴다고 적고 있다. 화면이 깔끔하다는 사실만으로 배너가 실제 기기에서 버튼을 가리지 않는다고 판단할 수 없는 이유다.

2026년 8월 스토어 자료의 브라우저 캡처. 초기 SwiftUI 앱이나 제출 빌드의 실기기 검증 화면이 아니다.

이 이미지는 터치 버튼 배치와 소개 자료의 구성을 설명하는 데 쓸 수 있다. 네이티브 광고의 높이, 화면 복귀, 기기 성능을 증명하려면 해당 빌드의 기기명·방향·광고 상태가 붙은 별도 기록이 필요하다. 같은 이미지라도 무엇을 증명하는 자료인지 먼저 적으면 검토자가 잘못된 결론을 내릴 여지가 줄어든다.

업로드·심사 제출·승인을 따로 기록한다

보관 문서의 제출 표에는 2026년 8월 25일, 버전 1.0.7, 빌드 8, 업로드·심사 제출 완료가 적혀 있다. 이 문서로 확인하는 상태는 제출 기록까지다. 승인·스토어 공개·매출은 확인하지 않았다.

Apple의 빌드 업로드 안내에 따르면 업로드한 빌드는 처리 과정을 거쳐 App Store Connect에 나타난다. 따라서 다음 증거를 별도 칸에 두면 “올렸다”는 말의 범위가 분명해진다.

상태 확인할 자료
산출물 생성 아카이브 식별값, 버전, 빌드 번호
전송 성공 업로드 결과와 그 산출물의 일치 여부
처리 완료 App Store Connect에 나타난 빌드
심사 제출 제출한 버전과 선택한 빌드, 제출 상태
승인·공개 승인 상태와 실제 배포 설정·스토어 페이지

당시 기록에는 iPad 방향 설정으로 ITMS-90474를 겪고 수정한 내용도 있다. 설정 파일을 고쳤다는 사실과 최종 아카이브에 그 설정이 들어갔다는 사실은 다르다. 방향 설정의 산출물 검사는 ITMS-90474 아카이브 점검 글에서 따로 다룬다.

기존 빌드 7이 실제로 업로드됐는지는 보관 문서도 확정하지 않는다. 다음 번호를 정할 때는 로컬 숫자만 보고 과거 제출 상태를 추정하지 말고, 실제 계정의 빌드 기록과 대조해야 한다.

세 줄 요약

  • 웹 빌드·동기화·설치 앱의 식별값을 연결하면 오래된 번들이 남은 경계를 찾을 수 있다.
  • 광고 닫힘과 보상 이벤트를 구분하고, 복귀와 중복 지급은 게임 쪽에서 따로 검사한다.
  • 브라우저 캡처와 제출 문서는 각각의 범위에서만 증거로 쓰고 승인·공개 상태를 별도 확인한다.

    카드와 전투 이미지 수령 규격, 재생성 후보 비교, 물리 파일과 프레임 개수, 제작 자산과 설치 용량을 구분하는 원장.

    드로우·선택지·버림패·장착·제거 이력의 카드 ID를 검사하고 변형과 브랜치 통합 뒤 데이터 연결을 확인한다. Python 참조 모델의 4개 검사 포함.
