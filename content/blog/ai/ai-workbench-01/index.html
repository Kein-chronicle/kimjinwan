여러 제작 공정 합치기: 공통 검사·분야별 규칙·이식 검증의 경계

기록일 2026. 9. 7.수정 2026. 10. 13.

표시 날짜는 공장 통합 커밋의 날짜입니다. 2026년 10월 14일 보관 함수를 격리 실행하고 ai-game-factory-08의 이식 기록을 통합했습니다.

이 글의 목적

여러 제작 공정을 운영하는 개발자가 공통 검사를 한곳에서 유지하고 분야별 확장과 과거 판정·이식의 경계를 정한다.

핵심 내용

분야는 공통 검사를 대체하지 않고 추가한다. 기준이 바뀐 판정과 플랫폼이 바뀐 검증은 새 증거가 필요하다.

읽고 나서

분야 두 개에 공통 검사 변경을 적용하고 중복 ID와 기존 산출물 덮어쓰기가 거부되는지 확인한다.

  • 세 줄 요약

한 줄 요약: 여러 제작 공정을 합칠 때는 공통 검사를 덮어쓸 수 없는 추가 규칙으로 분야를 확장하고, 기준이 바뀐 과거 판정과 플랫폼 이식 검증을 따로 관리한다.

세 공장에 같은 검사 파일이 복사돼 있다. 한 곳의 결함을 고친 뒤 다른 두 곳에도 옮겼다고 생각했는데, 며칠 뒤 한 공장만 예전 결과를 낸다. 파일을 합치는 것만으로는 충분하지 않다. 무엇이 공통이며 어디까지 달라도 되는지, 이전의 통과 판정을 언제 무효화할지도 정해야 한다.

2026년 9월 7일 앱 공장 통합 커밋 95b811b의 문서와 합성 코드를 읽고 작은 격리 입력으로 네 검사를 실행했다. 별도로 Swift 게임 라인의 이식·홀드 기록을 대조했다. 현재 전체 공장이나 실제 앱 빌드를 재검증한 결과는 아니다.

단계는 공통 정의, 분야는 추가 규칙

당시 구조에서 factory/pipeline.json은 공통 단계·산출물·검사를 정의한다. profiles/<분야>/profile.json은 선정 기준과 기존 단계에 붙일 추가 검사를 정의한다. 각 앱은 factory.json으로 분야를 지정하고, 진행표에는 합성한 정의와 판정이 남는다.

여기서 프로필은 공장을 복제한 폴더가 아니다. 공통 기준 위에 더하는 작은 차이의 목록이다.

공통으로 둘 것 분야에 남길 것 제품마다 새로 판단할 것
단계 순서와 필수 산출물 형식 분야별 콘텐츠 추가 조건 해결할 사용자 문제
검사 실행과 결과 기록 특정 콘텐츠의 검사 함수 연결 이 제품을 선택할 이유
정의 변경 감지와 진행 잠금 전용 자료 경로·선정 기준 실제 화면·입력의 적합성
공통 배포 준비 절차 공통을 약화하지 않는 추가 요구 대상 빌드의 기기 검증

예를 들어 심리·놀이 분야는 당시 명세 단계에 psych.json 자료와 전용 검사를 더했다. 기능형 프로필은 별도 단계 추가가 없는 형태였다. 어느 쪽이든 같은 공통 검사를 물려받는다. 분야 파일이 개발·검증 명령 전체를 교체하는 구조로 두면 공통 검사를 우회할 길도 생긴다.

확장할 수 있어도 덮어쓸 수는 없게 한다

보관된 profiles.py의 compose()는 공통 정의를 읽고 분야별 추가 항목을 합친다. 이때 검사 ID가 기존 ID와 겹치면 오류를 낸다. 같은 단계의 산출물 경로를 다시 정의해도 오류다. 단계에 허용되지 않은 구조 변경 필드 역시 거부한다.

개념적으로는 다음 관계다.

기능형 실행 정의 = 공통 단계 + 기능형 추가 검사
심리형 실행 정의 = 공통 단계 + 심리형 추가 검사
금지: 심리형 추가 검사로 공통 검사 ID를 대체
금지: 같은 단계의 기존 산출물 경로를 다시 선언

산출물 충돌 검사는 같은 단계 안의 경로를 대상으로 한다. 이 코드만 보고 모든 단계·모든 파일의 충돌을 전역 차단한다고 설명하면 범위를 넘는다. 실제 새 분야를 붙일 때는 어떤 단계에 어떤 자료를 추가하는지 검토해야 한다.

보관된 합성 함수에서 네 가지를 확인했다

2026년 10월 14일, 해당 커밋의 합성 함수를 임시 폴더의 작은 입력에 연결해 실행했다. 공통 질문 하나와 두 분야만 둔 시험이다. 자동 검사 명령·실제 앱·Xcode는 실행하지 않았다.

입력 변경 실행 결과 확인한 범위
공통 질문 before를 after로 변경 두 분야 모두 새 질문을 읽고 정의 지문 변경 공통 변경 전파와 정의 차이 감지
B 분야에 B-ONLY 검사 추가 A는 공통 1개, B는 공통+전용 2개 분야 추가 규칙의 격리
분야에서 COMMON ID 재사용 ValueError 발생 기존 검사 ID 덮어쓰기 거부
분야에서 같은 단계의 base.json 재사용 ValueError 발생 기존 산출물 경로 덮어쓰기 거부

검사 출력은 네 PASS였다. 이는 합성 함수의 해당 입력에 대한 결과다. 전체 실행기의 이전 판정 이전 처리, 실제 검사 명령, 신규 앱의 품질까지 통과했다는 뜻은 아니다.

다른 공정에서도 정상 입력 하나만 넣지 말고 일부러 공통 검사 ID를 중복시켜본다. 추가 규칙이 허용되는지와 공통 규칙을 약화할 수 없는지는 별개의 질문이다. 둘 다 통과해야 새 분야를 안심하고 붙일 수 있다.

공통 정의가 바뀌면 과거 PASS도 다시 분류한다

통합 문서는 공통·분야 버전과 정의 지문, 검사 구현 지문을 진행표에 포함하도록 설명한다. 낡은 진행표는 migrate로 갱신하며, 질문이나 검사 구현이 바뀐 항목의 이전 통과를 무효화하고 해당 단계와 후속 단계를 잠그는 정책이다. 관련 없는 판단은 유지할 수 있다.

핵심은 “규칙 파일 최신”과 “이 앱이 최신 규칙을 통과함”을 구분하는 것이다. 예를 들어 스크린샷 검사가 파일 존재만 보다가 해상도까지 보도록 바뀌었다면, 예전의 통과 표시만으로 새 조건을 만족했다고 할 수 없다.

다음 표는 이전 판정을 처리할 때 사용할 검토 순서다.

  1. 앱이 마지막으로 확인한 정의·검사 구현 지문을 기록한다.
  2. 새 정의와 비교해 질문, 검사 코드, 필요한 증거 중 바뀐 항목을 찾는다.
  3. 영향을 받는 판정과 후속 단계의 의존 관계를 검토한다.
  4. 새 조건에 필요한 증거를 다시 얻고 해당 검사로 판정한다.
  5. 이전 출시·제출 산출물은 별도 보존하고 새 검사 결과와 섞지 않는다.

이번 네 검사에는 이 전체 이전 절차의 실행은 포함되지 않았다. 동결 앱을 자동으로 재검증하지 않는다는 당시 정책도, 그 앱이 영구적으로 새 기준을 만족한다는 뜻은 아니다. 수정·재제출을 시작할 때 어떤 기준을 적용할지 다시 정해야 한다.

다른 플랫폼에는 검사 질문을 옮기고 결과를 새로 얻는다

Swift 게임 라인에는 이전 공정의 단계·실행표와 게임 규칙 검토, 모바일 제출 경험을 참고한 기록이 있다. 하지만 웹에서 돌아가던 입력·화면·광고 코드를 복사했다고 Swift 앱의 같은 기능이 검증되지는 않는다.

옮길 자료 재사용할 부분 새 환경에서 다시 얻을 증거
규칙 문서 승패 조건과 상태 전이 질문 새 구현이 같은 조건을 만족하는지
아트 규격 표시 목적과 검수 항목 기기 해상도·입력·배치에 맞는 실제 화면
시험 경로 시작→행동→성공·실패→재시작 순서 손가락 조작과 상태 복구가 이어지는지
플랫폼 연동 무엇을 확인할지의 목록 실제 서명·번들·광고·제출 산출물

당시 스택 문서도 아이폰 실기기에서 웹뷰 입력 지연을 측정하지 않았다고 밝힌다. 따라서 언어를 바꿨다는 이유만으로 지연이나 성능이 개선됐다고 말하지 않는다.

Vat Relay의 홀드 문서에는 기계 검사 15개 통과와 사람의 플레이 판정 미기재가 함께 남아 있다. 진행 구조의 새 기준 때문에 디자인을 다시 검토해야 한다는 내용도 있다. 레지스트리의 홀드 표기는 8월 26일이고, 보류 폴더로 옮긴 커밋 d9ecd1f는 8월 31일이다. 상태 결정과 파일 정리는 다른 날짜다.

자동 검사 통과만 보고 다음 게임으로 복제했다면 빠진 판정도 함께 옮겼을 것이다. 재사용 목록에는 코드와 문서뿐 아니라 새 환경에서 반드시 다시 확인할 질문이 있어야 한다.

세 줄 요약

  • 공통 단계는 한 정의에서 읽고 분야는 추가 규칙으로 확장하며 기존 검사 덮어쓰기를 막는다.
  • 정의·검사 코드가 바뀌면 관련된 과거 판정과 후속 단계를 다시 검토하고 산출물을 구분한다.
  • 플랫폼을 바꿀 때는 규칙과 시험 질문을 재사용하되 입력·화면·연동의 증거를 새로 얻는다.
