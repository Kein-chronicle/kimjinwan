여러 사이트의 통계 코드 비교: 생명주기·중복 집계·날짜별 해시의 한계

기록일 2026. 9. 15.수정 2026. 10. 13.

2026년 10월 14일 코드를 재대조하고 합성 입력으로 해시를 검사했습니다. 이전 글의 날짜 간 연결 불가·브라우저 식별자 삭제 설명을 정정했습니다.

이 글의 목적

여러 사이트에 같은 통계를 붙이는 개발자가 전송 계약과 스택별 예외, 식별자 보관 범위를 따로 확인한다.

핵심 내용

같은 코드 원리도 생명주기와 저장 실패에서 다르게 동작한다. 날짜별 HMAC은 키와 원래 식별자가 남으면 다시 계산할 수 있다.

읽고 나서

이벤트별 기대 전송 횟수와 저장 위치별 보관·삭제 범위를 적고 재진입·경로 변경·저장 실패를 검사한다.

목차
  • 공통 계약과 스택별 어댑터를 분리한다
  • 두 클라이언트의 차이를 계약으로 읽는다
  • 날짜가 다른 해시와 날짜 간 연결 불가는 다르다
  • 삭제와 고유 방문자 수의 범위도 분리한다
  • 여러 저장소에 적용할 때 남길 검사표
  • 세 줄 요약

한 줄 요약: 같은 통계 기능도 스택별 생명주기·중복 억제·저장 실패를 따로 검사해야 하며, 날짜를 섞은 고정키 HMAC을 날짜 간 연결 불가와 같은 보장으로 설명하면 안 된다.

정정: 이전 글은 고정 비밀키와 날짜로 만든 해시를 날짜 간 재식별 불가라고 설명했고, 서버 이벤트 삭제가 브라우저 식별자 삭제까지 포함한다고 썼다. 둘 다 잘못된 설명이다. 키와 원래 식별자가 남아 있으면 과거 날짜의 값을 다시 계산할 수 있고, 서버 테이블 삭제는 브라우저 저장소를 지우지 않는다.

이 글은 2026년 10월 14일 네 저장소의 통계 코드를 대조하고, 공개 예시 키·가상 식별자로 보관 해시 함수를 실행한 결과다. 실제 방문자의 식별자나 운영 비밀키는 사용하지 않았다. 통계 기능의 동작 경계와 데이터 보관 범위를 나눠 설명한다.

공통 계약과 스택별 어댑터를 분리한다

대상은 정적 홈페이지, Astro 블로그, React 기반 웹 도구, 이벤트를 받는 Python 서버다. 이번에 읽은 정적 사이트 두 스크립트는 파일 해시가 같았다. React 쪽은 useEffect 안에서 전송과 이벤트 등록을 하고, 반환하는 정리 함수에서 리스너를 제거한다.

파일 모양이 다르다고 기능이 다르거나, 코드가 닮았다고 동작이 완전히 같다고 결론 내릴 수는 없다. 먼저 공통 계약을 적고 각 환경에서 그 계약을 확인한다.

공통으로 정할 것 스택에 맞춰 구현할 것 검토할 질문
이벤트 종류와 필드 스크립트 실행 또는 컴포넌트 연결 어느 시점에 한 번 보내는가?
도구 사용의 중복 기준 세션 저장소와 메모리 처리 저장 실패 때도 같은 기준인가?
어떤 조작을 집계할지 DOM 선택자와 이벤트 등록 페이지 밖 조작도 섞이는가?
방문자·세션 식별 정책 브라우저 저장소 접근 언제 만들고 언제 지우는가?
서버 보관·조회 기준 저장소와 집계 코드 하루·여러 날의 고유 수를 어떻게 정의하는가?

React의 useEffect 문서는 외부 시스템 연결과 정리 함수를 설명한다. 개발 환경의 Strict Mode에서는 추가 설정·정리 주기가 실행될 수 있다. 리스너를 지우는 코드가 있다는 사실만으로 이미 전송된 네트워크 이벤트가 취소되거나 중복이 제거되는 것은 아니다.

두 클라이언트의 차이를 계약으로 읽는다

읽은 구현은 page_view와 tool_use를 보낸다. 중복 억제 조건은 tool_use에만 걸려 있다. 두 이벤트 모두 저장 표시를 남기지만 페이지뷰는 그 표시를 보고 반환하지 않는다. 따라서 “세션당 모든 이벤트 한 번”이라는 요약은 틀린다.

경로 정적 스크립트 React 컴포넌트 추가 검사
처음 연결 즉시 페이지뷰 전송 Effect 설정 때 페이지뷰 전송 재연결·개발 모드에서 중복되는지
도구 조작 도구 호스트의 .tool-page 내부 입력 .tool-page 내부 입력 실제 배치한 페이지에서 범위가 맞는지
정리 문서 수명에 붙은 전역 리스너 Effect 정리 때 리스너 제거 반복 연결 후 리스너 수
저장 함수 실패 읽기·쓰기 보조 함수에 메모리 대체값 저장 호출 실패를 잡고 진행 도구 사용 중복 억제가 같은지
앱 안의 경로 변경 별도 경로 구독 없음 빈 의존성 배열, 경로 변경 구독 없음 전체 새로고침 없이 이동할 때 페이지뷰

마지막 두 행은 단순 복사의 위험을 보여준다. 읽은 React 코드에는 정적 버전과 같은 메모리 중복 억제 장치가 없다. 또한 두 코드 모두 저장소 객체를 얻는 바깥 접근까지 모든 차단 상황에서 안전한지는 별도 브라우저 검사가 필요하다. 주석에 “익명”이라고 적혀 있다는 이유로 저장 차단 동작을 검증한 것으로 보지 않는다.

이 표는 코드 대조 결과와 다음 검사 목록이다. 이번에 실제 브라우저의 모든 저장 차단·라우팅 조합을 실행한 결과는 아니다.

날짜가 다른 해시와 날짜 간 연결 불가는 다르다

서버의 함수는 다음 형태다.

hmac.new(secret, f"{day}:{value}".encode(), hashlib.sha256).hexdigest()

같은 식별자라도 날짜가 바뀌면 결과가 달라진다. 하지만 결과가 다름과 나중에 연결할 수 없음은 별개다. 고정 키와 원래 식별자를 알고 있으면 같은 함수를 과거 날짜로 다시 계산할 수 있다. 이 설명은 해시를 역산한다는 뜻이 아니다.

보관 함수에 공개 예시 키와 가상 방문자 문자열을 넣어 실행했다.

검사 결과
같은 식별자·키로 이틀의 해시 비교 서로 다름
같은 식별자·키와 첫날 날짜로 다시 계산 첫날 값과 같음
같은 식별자·키와 둘째 날 날짜로 다시 계산 둘째 날 값과 같음

두 날짜 비교와 두 날짜 재계산을 묶은 검사 두 건이 통과했다. 별도로 정적 파일 둘의 바이트 일치 검사도 통과했다. 운영 데이터를 조사한 결과가 아니라 함수의 성질을 확인한 합성 입력 검사다.

Plausible의 데이터 정책은 지속 방문자 식별자를 만들지 않고 로컬스토리지를 쓰지 않으며, 일일 솔트를 교체·폐기하는 방식이라고 설명한다. 이 프로젝트는 브라우저에 UUID를 저장하고 고정 비밀키에 날짜를 넣는다. 데이터 재료와 보존 조건이 다르므로 같은 프라이버시 보장이라고 등치할 수 없다. 해당 서비스의 문서 설명을 이 구현의 법적 적합성 판단으로 옮기지도 않는다.

삭제와 고유 방문자 수의 범위도 분리한다

읽은 서버 코드는 새 이벤트를 추가할 때 400일보다 오래된 이벤트 행을 삭제한다. 이것은 테이블의 정리 조건이다. 정확히 400일이 되는 순간마다 별도 작업이 실행된다는 뜻은 아니고, 브라우저의 localStorage UUID를 삭제하는 코드도 아니다.

저장 위치 읽은 코드의 처리 이 코드로 확인할 수 없는 것
브라우저 방문자 UUID localStorage에 만들고 재사용 자동 만료·서버 삭제와 연동한 제거
브라우저 세션 UUID sessionStorage에 만들고 재사용 모든 브라우저 수명 조건의 실행 결과
서버 이벤트 해시한 방문자·세션 값 저장, 추가 시 오래된 행 삭제 백업·접근 로그 등 다른 보관소의 정책
집계 결과 기간 안의 서로 다른 방문자 해시 수 그 기간의 실제 사람 수

서버의 여러 날 집계는 COUNT(DISTINCT visitor_hash)를 사용한다. 동일한 브라우저라도 날짜가 달라 해시가 달라지면 여러 개로 셀 수 있다. 따라서 7일의 이 값을 “7일 동안 방문한 실제 사람 수”로 표시하면 의미가 맞지 않는다. 날짜별로 나뉜 식별값을 센다는 정의를 UI와 분석에 반영해야 한다.

여러 저장소에 적용할 때 남길 검사표

먼저 이벤트 필드·전송 시점·중복 키·저장 수명을 공통 계약으로 적는다. 그다음 정적 페이지의 재로드와 React의 연결·정리·경로 변경을 각각 검사한다. 마지막으로 서버가 원문·해시·이벤트를 어디에 얼마 동안 보관하는지 확인한다.

최소 시험 입력은 최초 진입, 재진입, 도구 버튼 두 번, 다른 도구로 이동, 저장 접근 실패, 전송 실패다. 기대 전송 횟수와 실제 전송 횟수를 비교하고, 네트워크 전송을 흉내 낸 검사와 실제 수집 서버 확인을 구분한다. 기능을 네 곳에 넣었다는 완료 보고보다 이 계약과 예외 경로가 유지보수에 더 유용하다.

세 줄 요약

  • 같은 이벤트 계약도 정적 실행·React 생명주기·경로 변경·저장 실패에서 각각 검사한다.
  • 고정 키·식별자가 남으면 날짜별 HMAC을 다시 계산할 수 있어 날짜 간 연결 불가로 설명할 수 없다.
  • 서버 이벤트 삭제·브라우저 식별자 수명·여러 날의 고유 수는 서로 다른 범위로 정의한다.

같이 읽을 글

  • set -e 스크립트가 에러 없이 중간에 끝날 때: 변수에 담은 grep 한 줄 찾기

    set -e를 켠 bash 검사 스크립트가 통과해야 할 때만 아무 메시지 없이 멈췄다. macOS bash 3.2·zsh·sh로 원인(grep의 매치 없음 종료 코드 1)과 세 가지 수정, 수정이 삼키는 오류를 재현했다.

  • macOS에서 grep -P가 안 될 때: 오류가 나는 경우와 조용히 비거나 엉뚱한 결과가 나오는 경우

    macOS 기본 grep에서 grep: invalid option -- P 가 나올 때 대체 방법과, 오류 없이 비거나 엉뚱한 결과가 나오는 \d+·\K 같은 정규식을 이 맥에서 직접 실행해 가려냈다.

  • SwiftUI 공유 시트가 비어 있을 때: item으로 공유 데이터 함께 넘기기

    첫 공유가 빈 시트인 경우를 자체 예제로 대조하고, 선택한 문자열과 Copy 출력까지 확인하는 item 기반 구현을 제공한다.
